# Согласованный план SmartDNS WebUI

Обновлён 29.10.2026. Актуальные решения и приоритеты; прежний план с прототипом Go заменён этим документом. Журнал обсуждения: [DECISIONS.md](DECISIONS.md).

## Приоритеты

### 1. Удобная авторизация

- Страница входа в общей теме вместо браузерного HTTP Basic-диалога. Проверять существующий пароль Entware, не создавать вторую копию пароля в настройках.
- До реализации изучить хранение сессии в nfqws2 WebUI. Его фактическое устройство пока не проверено; не выдавать предполагаемое поведение за установленное.
- После закрытия и открытия браузера повторный вход обычно не требуется. Сессия должна переживать перезапуск роутера; срок действия согласовать отдельно, конкретные 30/90 дней не выбраны.
- Постоянная cookie содержит непрозрачный случайный токен, не пароль. Защищённое серверное хранение сессий, HttpOnly/SameSite, Secure при HTTPS; срок действия и отзыв, ограничение подбора пароля, CSRF/Origin-проверки для изменений.
- Кнопку «Выйти» в шапку не добавлять. При необходимости — действие «Забыть этот браузер» в настройках.
- Истечение сессии не должно молча уничтожать открытый черновик.

### 2. Готовый IPK и автономная установка

- Упаковать существующий CGI/JS WebUI: отдельные бинарники для разных CPU ему не нужны. Рассмотреть Architecture: all с проверенными зависимостями и явно указанной совместимой средой Keenetic/Entware.
- Сборка должна позволять другим пользователям установить WebUI с чистого окружения, не включая личные настройки, пароли, ключи и резервные копии разработчика.
- Установка/обновление/удаление сохраняют пользовательские DNS-конфиги и списки. Проверка результата, артефактов, резервная копия и откат версии UI.
- Убрать зависимость от доступности CDN: включить необходимые статические файлы в пакет с учётом лицензий и размера.
- Переписывание на Go, собственный сервер и сборки бинарников под разные CPU исключены из ближайшего плана. Возвращаться к этому только при конкретной доказанной пользе и замерах ресурсов.

### 3. Понятное применение и восстановление

- Однозначно различать «сохранено», «применено», «проверяется», «отказ» и «откат»; показывать текущий этап и оставшееся время, когда оно достоверно известно.
- Восстанавливать подтверждённое состояние после перезагрузки страницы по серверной транзакции.
- История конфигураций: выбрать версию, просмотреть diff и восстановить через проверку и откат; ограничить объём хранения.
- Ускорение проверок оценивать отдельно, не ослаблять защиту рабочего DNS. Watchdog применения остаётся независимым от вкладки браузера.

### 4. Документация провайдеров и источники списков

- Раздел с активными проксирующими DNS-группами без закомментированных серверов: назначение, официальный проект провайдера, фрагмент конфига и команды добавления с резервной копией и защитой от дубликатов.
- До публикации отделить общедоступные адреса от персональных ссылок/токенов и платных подписок. Конкретные группы ещё не выгружались и не публиковались в рамках этого решения.
- Geohide: проверить доступный способ получения сервисов и списков; начать с выбора сервисов и проверки обновлений по кнопке.
- Добавить универсальный импорт списка по URL. Другие надёжные каталоги сначала исследовать; готового подтверждённого альтернативного источника пока не выбрали.
- Показывать diff до принятия; ручные дополнения/исключения хранить отдельно и сохранять. При недоступности, пустом или некорректном ответе источника остаётся последняя принятая версия.
- Источники вынести в отдельный раздел. Постоянный опрос и расписание по умолчанию не добавлять.

### 5. Резервирование проксирующих DNS

- Помечать DNS-группы как проксирующие и правила как требующие таких DNS. Это свойство результата работы сервиса, а не просто DoH/DoT.
- Для правила задать основную группу и упорядоченный набор разрешённых резервных групп; обычная DNS-группа не подменяет требуемую проксирующую.
- Сначала ручное назначение и проверка по запросу. Автоматизация позже: несколько подтверждённых неудач, пауза между переключениями, понятная причина, поведение при отказе всех групп и возврате основной.
- Успешный DNS-ответ сам по себе не подтверждает доступность целевого сервиса. Критерии проверки ещё нужно разработать.

## Дополнительные улучшения

- Журнал: отделить клиентские запросы от внутренних событий SmartDNS; понятные поля домена, устройства и группы без постоянного опроса.
- Перед удалением DNS-группы или списка показывать использующие их правила.
- Поиск по нескольким файлам, различение повторов и намеренных пересечений; не удалять автоматически.
- Реальная мобильная приёмка означает физический телефон, экранную клавиатуру, выделение пальцем и изменение высоты мобильного браузера. Эмуляция размеров на компьютере этого не заменяет.
- Редкие действия и технические подробности раскрывать по необходимости, не перегружать основные страницы.

## Границы проекта

- Использовать SmartDNS из официального репозитория Entware. Обновление до 48.4, собственная сборка/форк SmartDNS исключены из ближайшего плана WebUI; при реальной необходимости это отдельная задача/проект.
- Специальный блок Fallback удалён в 1.8.10. Импортированная обычная группа с именем fallback сохраняется среди других групп; её название не обещает резервирование.
- Основные требования: ограниченные CPU/RAM, сохранность конфигураций и понятные действия. Новая функция не должна требовать фонового демона без обоснования.
- Готовые изменения после проверок доводить до main; сохранять связность истории обычным merge и убирать завершённые ветки. План не является разрешением менять рабочий DNS.
